# 改版整理 /updates（2026-11-09）

## 為什麼做

使用者看到楓情報的「新版資訊與改版整理」（kafuffu20.com/updates.html?patch=2026-10-15），問這種頁是怎麼做的。
答案是拿遊戲更新前後的資料逐筆比對。我們 repo 的 `public/data` 歷史裡本來就有三個版本
（1.13.1 `1fd6dc25`、1.15.2 `fa4bd7b3`、2.0.0 `5b5b5e2d`），不用更新本機客戶端就能比。

玩家想知道的是：這次更新多了什麼、跟我有沒有關係、哪些東西改了數字。

## 使用者拍板的（11/09）

- **版面：D 進去是 A。** `/updates` 是改版紀錄（每版一張卡，照時間新到舊）；點進去 `/updates/<版本>` 是那一版的重點頁
  （這次重點 4 條 → 改了多少 → 說明改了的道具 → 全部新東西）。候選圖在 `assets/2026-11-09-patch-notes/`（A.png、D.png 是採用的兩張；B、C 沒選）。
- **重點 A：資料換版本後，我（Claude）寫 4 條重點草稿開 PR，使用者審完合併才上線。** 沒寫重點的版本不出現。
- **位置 A：攻略專區多一個分類「改版整理」，網址 `/updates`、`/updates/<版本>`，每版一頁給 Google 收錄。導覽列不動。**

## 我的判斷（使用者沒逐條看過，可推翻）

- **兩邊都用「現在的處理程式」重建再比**（寫手檢查後改的）：直接比 `public/data` 的 git 歷史會混進我們自己改處理程式造成的差
  （1.13.1→1.15.2 有 1,196 件只是「未命名道具」補了名字）。上游 repo（`morrisrrrrrrr-svg.github.io`）的 `data.js` 歷史每一版都在
  （1.14.5、1.14.7、1.15.0、1.15.1、2.0.0…），所以取「每個 gameVersion 的最後一個上游 commit」當那一版，用現在的 `build.mjs` 各跑一次再比。
  這樣比出來的才是遊戲的差。
- 版本範圍：上游歷史裡 gameVersion 有換的每一版都做（約從 1.14.5 起），舊版的上游格式現在的 `build.mjs` 吃不下就跳過那一版、在 PR 寫明。每版都要有重點檔才會出現。
- 同一個 gameVersion 內上游又修正（例如 2.0.0 之後 10/16、10/21 又改掉落）：**用該版最新的資料重算**，基準永遠是「前一版的最後一個上游 commit」。
  這樣改版頁跟站上道具頁的值一致。`index.json` 記每版用了哪兩個上游 commit。
- 候選圖上的 432／172／648／82 是用舊方法估的，重建後會變；驗收以 `build-patch.mjs` 重跑的數字為準，重點檔裡的數字寫草稿時再對一次。
- 「改了」只列看得懂的欄位：說明（`d`）、商店（`sp`／`price`）、掉落（`dm`）、能力（`eq`）、名稱（`n`）。
  任務關聯（`qr`、`qq`）、`un`、分類（`c`）這些內部欄位不列、也不算進「改了多少」。
- 站上資料比對時不見的東西，一律寫「站上不再列出」，不寫「移除」：2.0.0 那 82 個任務是上游拿掉的未開放地區任務，不是遊戲刪掉。
- 新增道具數字分開寫：一般道具（432）跟髮型臉型（`s` 為「外觀/角色」，709）分開，髮型臉型只給數字不列清單。
- 版本日期：預設用那一版第一個上游 commit 的日期，標「收錄」；重點檔可以寫官方改版日蓋掉，蓋掉才拿掉「收錄」兩個字。
- 跟楓情報一樣每頁底下一行：「比的是更新前後的遊戲資料，不是官方公告；什麼時候開放、怎麼拿到，以遊戲內為準。」

## 不做的

- 不做「跟我有關」（候選 B）。之後可以加在單版頁裡，這次不加。
- 不補我們資料裡沒有的東西（例如楓葉武器本體 19 把、伊卡路斯披風那批不在 `items.json`）。不從客戶端另抽、不手打。
- 不寫產品沒有的內容：沒有資料支撐的「怎麼取得」「開放時間」一律不寫。
- 導覽列不加按鈕。
- 不改資料自動更新合進 main 的方式。

## 會算失敗的

- 數字跟資料對不起來（每個數字都要能用比對腳本重算出來）。
- 把「站上不再列出」寫成「遊戲移除」。
- 文案出現內部用語（欄位名、上游、管線、客戶端版本號以外的工程字）。
- 改版頁讓其他頁變慢：差異檔只在 `/updates` 相關頁讀，不進首頁、不進全站共用資料。

## 資料怎麼來

### 差異檔（自動）

- 新腳本 `pipeline/build-patch.mjs <舊資料夾> <新資料夾>`：比 `items.json`、`quests.json`、`monsters.json`、`maps.json`，
  輸出 `public/data/patches/<新 gameVersion>.json`，外加 `public/data/patches/index.json`（各版本號、前一版號、收錄日、各類數字）。
- 差異檔內容：新增（id、名稱、分類、子分類、等級）、站上不再列出（id、名稱）、改了（id、名稱、哪一類、舊值→新值的白話字串）。
  舊值→新值要寫成能直接顯示的字，例如「恢復 HP、MP 各 1500 → 1200」不容易自動產，所以**說明類只存舊說明、新說明全文**，
  畫面上用逐字比對標出不同的地方；商店、能力類存結構化的舊值新值。
- 以 `id` 比對；`maps.json` 是物件（key 是地圖 id）。
- 新腳本 `pipeline/build-patch-base.mjs <上游 commit> <輸出資料夾>`：從上游 repo 取那個 commit 的資料檔，用現在的 `build.mjs` 重建到暫存資料夾
  （不碰 `public/`，也別讓它的 syncAssets 刪 `public/assets`，見記憶「上游資料改版會漏抽欄位」裡的坑）。
- 資料自動更新（`.github/workflows/data-refresh.yml`）：`build.mjs` 之後，用 `build-patch-base.mjs` 重建「前一版的最後一個上游 commit」當基準，
  再跑 `build-patch.mjs` 重算現在這一版的差異檔（換版、同版修正都重算）。上游 clone 要能看到歷史（現在是淺 clone，要另外抓那一個 commit）。
  差異檔是 json，符合 artifact 只收 png／json／webp 的規定。
- 歷史版本用同一套腳本一次性產出、commit 進 repo。
- 換了 `public/data` 要一起換 `meta.json` 的 `builtAt`（記憶「改資料要換版本號」，PR 單元測試會擋）。

### 重點檔（人審）

- `src/content/patches/<版本>.md`：front matter 有 `title`（例「萬聖節祭典、冰原雪域任務」）、`date`（官方改版日，可省略）、
  `highlights`（4 條，每條 `icon`：道具 id、`title`、`sub`）；本文可以空。
- 沒有重點檔的版本：`/updates` 不列、`/updates/<版本>` 404、不進 sitemap。
- 重點每一條都要能在差異檔裡找到依據（例：「楓葉武器專用卷軸 21 張」要真的有 21 筆新增卷軸）。測試擋：重點的 `icon` 道具 id 必須在該版差異檔的新增或改了裡。
- 誰寫：差異檔進來後，我起草重點檔、開 PR 到 dev，PR 內文列每條重點的依據數字。使用者審過才合。
  通知方式：資料自動更新那次如果產了新差異檔，就開一張 GitHub issue「新版本 X 要寫改版重點」（跟現在「失敗開 issue」同一套）。

## 畫面

照設計系統 A（`docs/superpowers/specs/2026-11-09-design-system-a-design.md`）：實心卡、1px 框、8px 卡片圓角、選中橘框淡底、不用膠囊。深淺兩套都要過 `contrast-audit.mjs`。

### `/updates` 改版紀錄（候選 D）

- 麵包屑「攻略 › 改版整理」，標題「改版紀錄」，一行說明。
- 每版一張卡：日期（最新那張日期橘色、卡片橘框）、版本號標籤、重點檔的 `title`、一行數字（新道具、新任務、新怪物＋怪名）、6 格道具圖、「看這次改了什麼 ›」。
- 6 格圖：先用重點檔 4 條的 icon，不夠再從新增道具挑（有圖的、排除髮型臉型）。

### `/updates/<版本>` 單版頁（候選 A）

1. 麵包屑、標題「M/D 改版整理（版本）」、一行說明。
2. 版本選單（切到其他有重點檔的版本）。
3. 「這次重點」：4 條，圖示＋標題＋小字＋來源標籤「客戶端資料」（藍）。
4. 「改了多少」：四格數字（新道具不含髮型臉型、新任務、新怪物、道具說明或數值有改）。
5. 「說明改了的道具」：先列 2～3 筆，「看全部 N 項 ›」展開；展開後可依 說明／商店／掉落／能力 篩。
6. 「全部新東西」：照分類收合（道具照子分類、任務照地區、怪物），每一類標數量，點開才列；道具有單獨頁就連過去（`<a>`）。
7. 「站上不再列出」：收合，一行說明為什麼。
8. 底下那行免責。

手機 375 寬第一屏要看得到標題和「這次重點」前兩條。
